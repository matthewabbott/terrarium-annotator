# 2026-01-03 - F10: Glossary v2 (Split Glossary/Codex)

## Objective

Redesign the glossary system to distinguish between two types of entries:
1. **Glossary**: Jargon/vocabulary terms that would confuse readers
2. **Codex**: Wiki-style entries for named entities

## Context

Quality issues identified in existing glossary (656 entries):
- Trivial entries: "75 silver transaction", "60% refund policy"
- Near-duplicates: "Vys Array" vs "Vys Array Transformation"
- No distinction between vocabulary (for embedding tuning) and wiki content

Critical problem: **Semantic jargon** - common English words with domain-specific meanings:
- "soul", "husk", "shell", "shard" in fantasy settings
- "egress", "redlines", "chartfield string" in building code
- These won't be flagged by dictionary checks but are exactly what we need for embedding vocabulary tuning

## Decisions Made

### Decision: Same table vs separate tables for glossary/codex
**Options considered**:
1. Separate `glossary_entry` and `codex_entry` tables
2. Same table with `entry_type` column
**Chose**: Option 2 - same table with entry_type column
**Rationale**: Simpler migration, shared search/FTS, entries can be reclassified

### Decision: Dictionary for novel term detection
**Options considered**:
1. NLTK words corpus
2. Custom wordlist
3. External API (dictionary.com, etc.)
**Chose**: Option 1 - NLTK words corpus
**Rationale**: Well-maintained, 236K words, no API latency, offline-capable

### Decision: Fresh database for v2
**Chose**: Start fresh database, no migration of existing 656 entries
**Rationale**: Cleaner approach, existing entries have quality issues anyway
